# PROJECT: DhakaLife — Dhaka Daily Life Super App

## ROLE AND OBJECTIVE

Act as a senior Android architect, Flutter engineer, UI/UX designer, backend engineer, API integration specialist, cybersecurity engineer, and QA automation engineer.

Build a production-oriented Android application called **DhakaLife** for residents of Dhaka, Bangladesh.

The app must provide useful, frequently needed daily-life services through one clean, modern, fast, accessible, and Bangla-first interface.

Use the attached Pathao-style app screenshot as the primary visual inspiration. Recreate its visual principles—compact service cards, rounded corners, clean spacing, strong visual hierarchy, colorful service icons, a prominent location-aware dashboard, and quick actions—without copying its logo, proprietary assets, or exact branding.

IMPORTANT:
- First inspect the existing project, if one exists.
- Understand its architecture, screens, dependencies, database, and working features before changing anything.
- If this is an existing application, extend it incrementally. Never delete working features, replace an established database, or rewrite the application unnecessarily.
- If the project is empty, establish a clean, maintainable architecture.
- Do not create a UI-only demo that falsely claims to have functional APIs or live data.
- Implement working features wherever possible and clearly label unavailable integrations.

Primary market: Dhaka, Bangladesh.

Target users:
- Students and office workers.
- Families and senior citizens.
- Daily public transport users.
- Residents looking for emergency assistance.
- People looking for nearby shops, hospitals, pharmacies, and household service providers.

Localization requirements:
- Bangla must be the default language.
- Provide English as an optional language.
- Support Bangla Unicode correctly on every screen.
- Use BDT (৳) for monetary values.
- Use the Asia/Dhaka timezone.
- Use familiar Bangladeshi location names and administrative areas.
- Provide a location search that supports Bangla and English spellings.
- Design for budget Android phones and inconsistent mobile internet.
- Do not require login to use public information, maps, calculators, and basic emergency-directory features.

## 3. CORE FEATURES AND IMPLEMENTATION REQUIREMENTS

### FEATURE A: MAP AND NEARBY PLACES

Use OpenStreetMap-compatible mapping technology.

Functions:
- Display the user's current location when permission is granted.
- Search for nearby hospitals, pharmacies, ATMs, markets, restaurants, bus stops, metro stations, and other useful points of interest.
- Support map and list views.
- Show walking or driving routes when a suitable routing service is available.
- Display distance, source, and last-updated information.
- Let users search a manually selected area without granting location permission.

Potential integrations:
- OpenStreetMap.
- Overpass API for points of interest.
- OSRM or another suitable routing provider.
- Android native location services.

Engineering requirements:
- Respect public API usage policies and rate limits.
- Do not query Overpass repeatedly for every map movement.
- Cache suitable search results.
- Debounce user searches.
- Handle missing coordinates and incomplete place data.
- Provide attribution where required.
- Never expose the user's exact location publicly without explicit consent.

### FEATURE B: DHAKA PUBLIC TRANSPORT GUIDE

Provide:
- Bus route and stop search.
- Origin and destination selection.
- Available route alternatives.
- Metro station directory and route information.
- Estimated distance and travel duration when supported.
- Fare information only when backed by reliable, dated data.
- User-submitted route corrections with moderation.

Important:
- Do not invent bus routes, fares, operating hours, or live vehicle positions.
- Distinguish verified data from community contributions.
- Where live data is unavailable, display static route information and clearly label it.
- Store route data in a maintainable, updateable database.

### FEATURE C: WEATHER AND FLOOD ALERTS

Potential provider: Open-Meteo or another suitable weather API.

Functions:
- Current weather.
- Temperature and humidity where available.
- Rain probability and forecast.
- Severe weather information when provided by a reliable source.
- Area-based waterlogging reports.
- Weather-related notifications with user consent.

Requirements:
- Cache the last successful response.
- Show the data source and update time.
- Handle unavailable API responses.
- Do not describe user-reported flooding as an official warning.
- Do not present forecasts as guaranteed outcomes.

### FEATURE D: EMERGENCY ASSISTANCE

Provide:
- Emergency contact directory.
- One-tap phone calls using the Android dialer.
- Nearby hospitals and emergency departments.
- Ambulance and fire-service contact information where verified.
- Optional location sharing with a selected trusted contact.
- Blood donor search with consent-based contact details.

Requirements:
- Verify emergency numbers against authoritative sources before release.
- Never fabricate emergency contacts or hospital capabilities.
- Clearly distinguish emergency services from general directories.
- Never delay access to emergency phone numbers behind login, advertising, or AI chat.
- Request only necessary permissions.
- Show an appropriate warning that the app is not a replacement for official emergency services.

### FEATURE E: NEARBY HOUSEHOLD AND ESSENTIAL SERVICES

Categories:
- Electricians.
- Plumbers.
- Carpenters.
- Mechanics.
- Household repair providers.
- Pharmacies.
- Clinics and hospitals.
- Other locally useful services.

Each listing may contain:
- Provider name.
- Service category.
- Service area.
- Phone number.
- Optional profile picture.
- Working hours.
- Indicative price, when supported.
- Rating and review count.
- Verification status.
- Last-updated time.

Support two types of listings:
1. Verified providers maintained by the app.
2. External or AI-assisted discoveries.

Clearly distinguish verified providers from unverified discoveries. Do not automatically describe an internet-discovered business as verified.

Provide reporting, duplicate detection, listing correction, and moderation features.

### FEATURE F: DAILY BAZAR PRICE

Allow users to explore prices of:
- Rice.
- Lentils.
- Eggs.
- Vegetables.
- Fish.
- Chicken.
- Other common household essentials.

Functions:
- Search products.
- Select market or neighborhood.
- Compare reported prices.
- Submit a price observation.
- View the observation date and source.

Validation:
- Never label an unverified price as an official government price.
- Detect suspicious values and duplicate reports.
- Allow administrators to verify or reject submissions.
- Show price freshness and confidence.
- Do not promise citywide price coverage without adequate data.

### FEATURE G: CIVIC ISSUE REPORTING

Allow users to report:
- Road potholes.
- Waterlogging.
- Garbage accumulation.
- Broken streetlights.
- Damaged public infrastructure.
- Other locally relevant civic issues.

A report can contain:
- Category.
- Description in Bangla or English.
- Optional photograph.
- Approximate location.
- Submission timestamp.
- Verification status.
- Report status.

Workflow:
SUBMITTED → UNDER REVIEW → VERIFIED or REJECTED → RESOLVED, where applicable.

Requirements:
- Prevent spam and duplicate submissions.
- Remove or restrict sensitive personal information in public reports.
- Obtain permission before uploading photographs or location information.
- Provide a report reference ID.
- Show whether the issue has merely been reported or officially acknowledged.
- Never claim a government department received a report unless an actual integration confirms it.

### FEATURE H: DAILY EXPENSE CALCULATOR

Provide an offline-first calculator for:
- Daily expenses.
- Household shopping.
- Monthly budget.
- Bill splitting.
- Expense categories.
- Spending summaries.

Requirements:
- Work without an account.
- Store data locally by default.
- Support export and optional backup.
- Clearly explain any cloud synchronization.
- Do not collect financial-account credentials.

### FEATURE I: GOVERNMENT INFORMATION DIRECTORY

Provide categorized public information about:
- Passport services.
- Birth registration.
- Government notices.
- Utility service information.
- Relevant citizen-service portals.
- Public transport or municipal notices where available.

Requirements:
- Prefer official government sources.
- Store source URLs and last-verified timestamps.
- Open official websites safely.
- Avoid scraping restricted websites.
- Do not imply that DhakaLife is a government application.
- Clearly distinguish information directories from official application or payment services.

### FEATURE J: BANGLA AI ASSISTANT

Build an optional assistant that can answer questions such as:
- "মোহাম্মদপুর থেকে মতিঝিল কীভাবে যাব?"
- "আমার কাছের হাসপাতাল কোথায়?"
- "আজ বৃষ্টির সম্ভাবনা কেমন?"
- "নিকটবর্তী ফার্মেসি খুঁজুন।"

Architecture:
- Use a pluggable LLM provider interface.
- Support an optional free-tier API if its current terms permit the intended use.
- Use retrieved, current, source-backed information for factual local answers.
- Integrate existing search, maps, weather, and directory services through controlled tools.
- Return concise answers in Bangla by default.
- Show sources, timestamps, and uncertainty.
- Ask before sharing location or personal information with an external AI provider.
- Never allow the AI to invent live traffic, opening hours, prices, availability, or emergency information.

If no API key is configured, the rest of the application must remain functional. Provide a clear configuration guide and an appropriate unavailable state.

## 5. FREE API STRATEGY AND FALLBACKS

Evaluate suitable providers for:
- Maps and points of interest.
- Routing.
- Weather.
- Geocoding.
- Backend and database.
- Push notifications.
- Optional AI.

Before integrating each provider:
1. Check its current official documentation.
2. Check rate limits and pricing.
3. Check commercial-use and attribution terms.
4. Determine whether an API key is required.
5. Determine whether caching is permitted.
6. Document its limitations.
7. Implement a provider abstraction where practical.

Security rules:
- Never commit API keys or service-account credentials to source control.
- Never place privileged backend secrets inside the Android APK.
- Restrict API keys where supported.
- Keep privileged operations on a secured backend.
- Do not bypass API quotas or access restrictions.

Fallback rules:
- Weather unavailable → show cached data with its original timestamp.
- Maps unavailable → provide a useful list view where cached data exists.
- Location permission denied → allow manual area selection.
- Internet unavailable → retain access to offline calculators, saved contacts, and cached information.
- AI unavailable → preserve all non-AI features.
- No verified route data → explain the limitation rather than generating fictional directions.

Create a provider status/configuration screen for administrators or developers.
